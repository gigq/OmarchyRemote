# Omarchy host backend

One Rust service connects the mobile shell to apps on the host. `apps.rs` is the table of host apps: the terminal programs the phone can open in their own PTY (`TUIS`) and the route-backed apps (`SERVICES`), plus the host name, home, and data directory. `terminal.rs` owns real PTYs; `herdr.rs` adapts the existing Herdr Unix socket; `files.rs`, `files_ops.rs`, `uploads.rs`, `browser.rs`, and `widgets.rs` serve the other apps. `main.rs` provides shared HTTP/WebSocket transport, origin checks, payload limits, capability discovery, and route registration. New app adapters belong alongside these modules under `/api/<app>/…`, and advertise their capabilities at `/api/capabilities`; see `../CONTRIBUTING.md`.

The HTML development server on loopback 4187 forwards `/api/` HTTP and WebSocket traffic to this service on loopback 4188. Both stay behind whatever private HTTPS address you publish (Tailscale Serve, for example). The Node process handles static files and live reload only; PTYs, Herdr access, and app APIs live in Rust. A future production static frontend can use the same API contract.

## Files API

- `GET /api/files?path=&hidden=false`: list a home-relative or absolute directory inside HOME, directories first. Returns root, canonical path, parent and entries.
- `GET /api/files/content?path=…`: regular-file bytes, up to 25 MiB; attachment/octet-stream, no-store, nosniff. The client renders text literally or uses an image blob.
- `POST /api/files/upload?path=…&name=…`: raw file bytes, up to 25 MiB, creates a private file without replacing existing names. Shares the upload writer with Herdr image attachments.
- `POST /api/files/folders` with `{ "path": "…", "name": "…" }`: creates a mode-0700 folder.

- `GET /api/files/search?path=…&query=…&mode=names|contents|everywhere|fuzzy&hidden=false&regex=false&sensitive=false&glob=…`: bounded results with optional content line hits, timing and truncation state. Names searches the current directory; contents recurses; everywhere/fuzzy use HOME. Skips build/cache/VCS trees; limits 50,000 entries, 3 seconds, 32 MiB scanned text and 100 hits.
- `GET /api/files/text?path=…`: UTF-8 text up to 1 MiB, SHA-256 version, permissions, owner UID and modification time.
- `POST /api/files/text` with `{ "path": "…", "text": "…", "version": "…" }`: checks the original version and atomically replaces the file, preserving permission bits. Rejects conflicting external edits.
- `POST /api/files/operate` with `{ "action": "copy|move|rename|trash", "paths": ["…"], "destination": "…", "name": "…" }`: up to 100 selections. Destination is used for copy/move; name for single-item rename. Returns completed paths and per-item errors. Never replaces destinations. Copy stages privately, then publishes atomically. Trash uses `gio trash` and remains recoverable on the host.
- `POST /api/files/archive` with `{ "paths": ["…"] }`: ZIP attachment with HOME-relative paths, capped at 25 MiB. Copy/archive reject symlinks and special files, and cap trees at 10,000 entries.

Paths are canonicalized and confined to HOME; external symlinks and the proxy-secret file (including aliases) are excluded. Upload names cannot contain path separators. Selection actions cannot operate on HOME or ancestors of the proxy secret. Writes are serialized within the backend; destination moves/renames use Linux no-replace semantics.

## App API v1

- `POST /api/uploads/files?name=<client file name>`: raw bytes of any type (maximum 100 MiB), returning `{ "path": "/absolute/host/path", "kind": "image" | "file" }`. `kind` is `image` when the bytes carry a PNG/JPEG/GIF/WebP/HEIC/HEIF signature. The name is reduced to one safe path component (last segment, unsafe characters replaced, at most 80 characters) and stored as `<uuid>-<name>`; unnamed uploads become `image-<uuid>.<ext>` or `file-<uuid>`. Files are unique mode-0600 entries under `$HOME/.local/share/omarchy-remote/uploads` (mode 0700), never served back, and persist until removed on the host. `POST /api/uploads/images` is the same handler for older shells.
- `GET /api/capabilities`: `{ version, host, home, apps }`, where `host` is the display name, `home` the backend user's home directory (the shell shortens paths with it), and `apps` the route-backed and PTY apps with their feature tags.
- `POST /api/terminal/session` with `{ "id": "optional previous ID", "app": "terminal" }`: create or resume a shell. Optional `cwd` selects a HOME-confined directory for a new Terminal shell. Any other `app` must be an id from `TUIS` in `apps.rs` (`btop`, `services`, `lazydocker`, `dua`, `lnav`); the program is resolved on `PATH`, `~/.cargo/bin`, `~/.local/bin`, `/usr/local/bin`, and `/usr/bin`, and a missing program returns `<program> is not installed on this host`. Unknown app values and cross-app resume IDs are rejected. Missing/expired IDs create a new session; the returned ID must replace the saved one.
- `WS /api/terminal/{id}/ws`: receive `screen` (UTF-8 bytes plus dimensions), `output` (bytes), `exit`, and `error`; send `input` (`data` string) or `resize` (`cols`, `rows`). A screen snapshot restores the terminal after reconnection. PTYs remain alive across app closure and live reload, until shell exit or backend restart. Up to eight shells may be open. Reconnection restores the current screen, not previous client scrollback.
- `GET /api/herdr/snapshot`: local Herdr workspaces, tabs, agents, and panes. A Claude pane whose agent still has background commands or agents running gets `background`, a list of `{ description, started }`, read from its transcript: a task starts with a tool result naming it (a background command's `backgroundTaskId`, a Monitor's `taskId`, or a background agent's `agentId`) and ends with a `<task-notification>` Claude Code queues for it that carries a `<status>` or reports the Monitor expired, or with a kill. A Monitor's other notifications are events while it keeps running. Tasks begun before the agent process started are dropped, as they ended with the earlier process. Kept for 4 seconds per pane; the WebSocket snapshots carry the same field.
- `GET /api/herdr/panes/{id}`: most recent 300 lines, with ANSI formatting.
- `POST /api/herdr/workspaces` with `{ "cwd": "…" }`: starts an unfocused Herdr workspace whose shell opens in that folder, named after it. The folder must exist inside the home directory. Returns the new root `pane` and a fresh `snapshot`.
- `POST /api/herdr/workspaces/{id}/tabs` with `{ "cwd": "…" }`: adds an unfocused tab to that Herdr workspace, its shell in the folder (which must exist inside the home directory). Returns the new root `pane` and a fresh `snapshot`.
- `POST /api/herdr/panes/{id}/input` with `text` and/or `keys`: literal text and Herdr key names. Text and Return can be sent atomically in one Herdr request. With `"typed": true` the text and keys are typed (Herdr `send_text`/`send_keys`), as Keys mode needs for editors; otherwise the text is pasted, bracketed when the program asks for it. Pasted text that names an image file by absolute path (as the attach button writes it) is pasted first, and the keys follow once Claude Code shows the new `[Image #…]` attachments, or the screen settles for up to 4 seconds; Claude Code drops a Return that arrives while it turns a pasted path into an attachment.
- `WS /api/herdr/ws`: snapshots (checked every 1.2 seconds), selected pane output (read every 16 ms for a second after each keystroke and every ~100 ms otherwise, sent only when its text changes; each update names the pane's `foreground` programs and whether a `fullscreen` program such as Vim owns the screen), heartbeat/error messages, and acknowledged input. Output is the pane's last 300 lines; send `{ "type": "history", "deep": true }` while the reader is scrolled back to receive up to 1,000 (Herdr's read limit, re-read every ~0.5 seconds when idle), and `deep: false` to return to 300. Send `select` with `pane_id`, then `input` with `id`, `pane_id`, `text`, and `keys`. `{ "type": "size", "pane_id", "cols", "rows" }` sizes the selected pane's terminal (5–500 columns, 5–200 rows) like a window: Herdr's socket API has no size, so the backend opens a `herdr terminal session control` at that size and releases it, and the pane keeps it. Sizes are applied one at a time, the latest winning; a pane another controller owns is left alone. Input is rejected if its pane no longer matches the selected pane. Pending input is never replayed after reconnection; an interrupted acknowledgement is reported as uncertain.
- `GET /api/muster`: Herdr agent threads by project: `projects`, each with `workspace_id`, `label`, `hidden`, the most urgent `state` of its threads (`question`, `ready`, `working`, or `idle`, in that order), `updated`, and `threads`. A thread has its `pane_id`, `tab`, `agent`, Herdr `status`, `state`, `title` (Claude's session title or a Codex goal), the person's last `prompt`, the agent's `latest` prose, `background` tasks, `updated`, and while it waits, the `question` read from its screen: `id`, `question`, `context`, `tabs`, numbered `choices` (`checked` for multi-select), `multi`, and the `other` choice that takes typed text. Conversations are read from Claude and Codex logs as Voice reads them; one that cannot be matched has an `error`.
- `GET /api/muster/panes/{id}`: one thread with its full prose (`paragraphs`, `updates`, `answer`, `working`), and the last 24 lines of its `screen` when it waits on something that is not a numbered menu.
- `POST /api/muster/panes/{id}/answer` with the question's `id` as `menu`, and `choose` (choice numbers; every choice to leave checked for multi-select) or `text` for the typed choice. The screen is read again first and nothing is sent if the menu changed (409). Choices are typed by number, multi-select changes are toggled and followed by Tab to the next question, and text goes through the typed choice and Enter. Returns the next `question`, or null.
- `POST /api/muster/panes/{id}/keys` with up to eight `keys` from `Up`, `Down`, `Left`, `Right`, `Enter`, `Escape`, `Tab`, and the digits; `POST /api/muster/panes/{id}/send` with `text`, pasted and entered as Herdr's Send does, and refused while the agent waits on a question.
- `POST /api/muster/panes/{id}/summary`: a Markdown `summary` of the thread before the person's last message, or null when there is nothing before it. It is made from the conversation log (the person's messages and the agent's prose, without tools or thinking; the first request and the latest turns when it is long) by a one-shot `claude -p` without tools, a saved session, or MCP servers (`--strict-mcp-config`; starting them took about three seconds) and without thinking (`MAX_THINKING_TOKENS=0`; Haiku otherwise spent most of its output on it), which brings a long thread's summary from 6–9 seconds to about 3, using `OMARCHY_MUSTER_SUMMARY_MODEL` (default `haiku`). Summaries are kept in `~/.local/share/omarchy-remote/muster-summaries.json` by the hash of what they summarize, so a thread is summarized again only after a new turn; at most two run at once. Threads report how many messages came before the last as `earlier`, and `answered: false` once the person has sent a message the agent has not replied to; `answer` is then the reply to the message before, and `latest` holds only the new turn's prose. The thread view's `turn_text` is everything the agent has written since the person's last message, as written, and `turn_parts` is the same as a list: `{ id, text }` for each message's text, and between them `{ work: { seconds, tools, files, thought } }` for work that used tools, thought, or took ten seconds or more (times from the log, files from edit tools and Codex patches), ending with the work in progress (`ongoing`, with `since`) while the agent works. A turn starts only with the person's own message, including pasted text; background-task notifications, reminders, interruptions, and compaction summaries continue it.
- `POST /api/muster/reviewed` with `threads`, each `{ pane_id, key }` from a thread's `review_key` (its latest answer's id, or Herdr's state counter when its log cannot be read): marks those turns reviewed, kept with hidden projects in `muster.json`. A thread's `state` is `question` (Herdr reports it blocked), `working`, `waiting` (finished, with background tasks still running), `review` (Herdr reports it done and its key is not marked reviewed), or `quiet`; a project takes the first of these its threads reach. A question's `kind` is `approval` for a Yes/No permission prompt. A thread whose last turn failed has a `failure` (`message`, `kind`), read from Claude's synthetic API-error replies and Codex's failed `task_complete`, and is in `question` unless the agent is working again or the failure was dismissed: `POST /api/muster/panes/{id}/dismiss` with its `key` (and the thread's `review_key`, to review it too). Only a blocked thread includes its `screen`.
- `POST /api/muster/hidden` with `workspace_id` and `hidden`: hides a project from the board or brings it back, saved in `~/.local/share/omarchy-remote/muster.json`. Herdr is not changed.
- `/api/canvas/…`: Canvas sessions, with the same routes as `/api/chat` over `~/Canvas` (or `OMARCHY_CANVAS_DIR`), offering Claude and Claude X. Claude runs with `--permission-mode bypassPermissions` and a brief appended to its system prompt (`OMARCHY_CANVAS_CLAUDE_ARGS` adds arguments). `POST /api/canvas/send` also takes `context`, the screen, device, and theme, which the agent receives in a `<canvas-context>` block before the message but which is not saved in the transcript. A session's `view` is the address of its page, `version` the newest change to its folder's files (other than the transcript), and `page` whether `index.html` exists; the WebSocket sends a `page` event with them after each tool result and turn. `GET /api/canvas/view/{id}/{token}/{path}` serves the session's files (`index.html` by default) to the page's frame without the client header, which a frame cannot send: the token signs the session with a secret made when the backend starts, and only files inside the session's folder, not its transcript or hidden files, are served. When a turn ends, its page (the folder's files other than the transcript and attachments) is copied to `.history/<turn>/`, with `.history/<turn>.json` holding the Claude session and last message uuid it ended at; sessions report these as `turns` (each `{turn, version}`, also sent in a `turns` event), and `view/{id}/{token}/@<turn>/{path}` serves a kept page. `send` with `from: <turn>` continues from that turn: it restores the page, cuts the transcript there, drops later turns (a `rewound` event gives the entry count and turns left), and starts Claude with `--resume <session> --resume-session-at <uuid> --fork-session --session-id <new>`, so the old session is left as it was; `.history/sessions` lists the sessions left behind, which archiving and deleting the canvas take along.
- `GET /api/chat`: `{ folder, available, agent, agents, models, efforts, defaults, chats }`. `agents` are those installed on the host: `claude` (Claude Code), `claudex` (Claude Code through a local proxy, from the `claudex` command), and `codex`, each with its `label`, `models`, `efforts`, and `defaults`; `agent` is the first of them. A Codex chat runs `codex exec --json` for each message in the chat's folder, resuming its session (saved in the chat's front matter once Codex names it), with pictures attached by `--image`; Codex offers no models unless `OMARCHY_CHAT_CODEX_MODELS` lists them, and its effort sets `model_reasoning_effort`. The top-level `models`, `efforts`, and `defaults` are Claude's. `models` are the `{ id, label }` choices, `efforts` the effort levels, and `defaults` the `model` and `effort` a chat on Default runs with (Chat's configured defaults, or Claude's own settings). Chats are read from the front matter of each chat folder's `chat.md` in `~/Chats`, newest first, each with `id`, `title`, `created`, `updated`, `preview`, its `folder`, and whether a reply is in progress (`busy`).
- `GET /api/chat/{id}`: one conversation's `entries` (`role` is `user`, `assistant`, or `tool`, with `time`, tool `name`, `text`, and a user message's `attachments`, paths such as `attachments/photo.jpg` in the chat's folder), plus `busy`, the reply streamed so far (`partial`), its delta count (`seq`), the number of the last event its state includes (`n`), and its `folder`.
- `POST /api/chat/send` with `text`, an optional `id`, optional `attachments`, an optional `agent` (one of `agents`; a new chat's agent, and for an existing one a move between `claude` and `claudex`, which share sessions; a Codex chat keeps Codex), and optional `model` and `effort` (one of `models` and `efforts`, or empty for Claude's default; anything else is refused). A chat keeps its settings in its file; sending different ones restarts its agent with `--model` and `--effort` and resumes the session, and is refused while a reply is in progress. Without an `id` it starts a conversation in a new folder named with its date and title (its first line) and returns the new `id`. `attachments` are up to 20 paths returned by `POST /api/uploads/files`; anything outside the uploads folder is refused, and `text` may be empty when there are attachments. Each file moves to the chat's `attachments` folder (a repeated name is numbered) and is linked below the message in `chat.md`. PNG, JPEG, GIF, and WebP files up to 3.75 MB go to Claude as image blocks, and the message lists every file's path. The message is saved before it is sent. A conversation's Claude Code process runs in the chat's folder with `--input-format stream-json`, keeps the conversation between messages, and exits after 15 idle minutes; the next message resumes the session. Web search and page fetches are allowed (`--allowedTools WebSearch,WebFetch`); other tools that would ask for approval are denied for now.
- `POST /api/chat/archive` and `POST /api/chat/delete` with `ids`: stop each chat's agent, then move its folder to `~/Chats/archives` (moving Claude's session log to the folder's new project, so it can still be resumed) or delete the folder, including files made in it, and Claude's copy: the session log and the session's folders in `projects`, `file-history`, and `session-env` under `~/.claude` (or `CLAUDE_CONFIG_DIR`). Returns `done` and `failed` (with each `error`), and sends a `removed` event.
- `GET /api/chat/{id}/response` and `POST /api/chat/{id}/speech`: Voice mode for a chat, as for a Herdr pane. The response is the latest reply's prose from the chat's Claude session log (`session`, `answer`, `paragraphs`, `updates`, and `working` while a reply is in progress); speech takes `response_id`, `response_ids`, and `stream` and returns WAV or streamed PCM from the configured speech command. Voice messages are sent with `POST /api/chat/send`.
- `GET /api/chat/{id}/attachments/{name}`: a file from the chat's `attachments` folder, with an image's content type.
- `POST /api/chat/{id}/stop`: stops the reply in progress. Text streamed so far is kept, and the session resumes from its last complete message.
- `WS /api/chat/ws`: events for every chat, each numbered in `n` (a client that loaded a chat applies only events numbered after its `n`): `entry` (with its `index`), `delta` (streamed text with a running `seq`, so a client that loaded `partial` skips deltas it already has), `busy`, `done` (with an `error` or null), and `resync` when the client fell behind and should reload.

Herdr uses its installed protocol-20 NDJSON socket API directly. Pane viewing/input does not focus or resize the desktop Herdr pane. Wide output remains horizontally scrollable. There are no fabricated agent approval buttons; use the actual pane's keyboard controls. This version attaches to existing agents/panes; agent creation and workspace management can be added through the same adapter later.

## Configuration and operation

`~/.config/omarchy-remote/backend.env` is a private mode-0600 environment file shared by the two user services. `OMARCHY_PROXY_TOKEN` (at least 32 characters) is required. It is sent from the local development proxy to Rust and never embedded in web assets or returned to clients. Only the local proxy knows it. Browser API requests require `X-Hyprland-Client: 1`; WebSockets require an allowed Origin. Cross-origin requests and unrecognized Host values are rejected. Whoever can reach the published HTTPS address can open a shell as the backend user, so the network (a tailnet, a VPN, a firewall) is the access control; this is a single-user application, not a public multi-user shell service.

Optional settings:

- `OMARCHY_API_PORT` defaults to 4188.
- `OMARCHY_ORIGINS` is a comma-separated list of full origins a browser may load the shell from; both services read it. Defaults to `http://127.0.0.1:4187,http://localhost:4187`, so the published HTTPS origin must be added here.
- `OMARCHY_HOST_NAME` is the name shown in the app's status lines and capabilities. Defaults to the kernel hostname.
- `OMARCHY_HERDR_SOCKET` defaults to `$HOME/.config/herdr/herdr.sock`.
- `OMARCHY_CHAT_DEFAULT_MODEL` and `OMARCHY_CHAT_DEFAULT_EFFORT` set what a chat left on Default runs with, such as `opus` and `high`; they must be among Chat's choices. Unset, Default follows Claude's own settings.
- `OMARCHY_CHAT_MODELS` replaces Chat's model choices with a JSON array of `[alias, label]` pairs, such as `'[["opus","Opus"],["sonnet","Sonnet"]]'`.
- `OMARCHY_CHAT_CODEX_ARGS` adds Codex arguments as a JSON array; to let Codex chats run every tool without asking, add `OMARCHY_CHAT_CODEX_ARGS='["--dangerously-bypass-approvals-and-sandbox"]'`. `OMARCHY_CHAT_CODEX_MODELS` offers Codex models as `[id, label]` pairs. Claude X needs only its `claudex` command, which sets up its proxy and permissions itself.
- `OMARCHY_CHAT_DIR` is the Chat folder, `~/Chats` by default; it must be inside the home directory. Each conversation is a folder there holding `chat.md`, and its Claude Code process runs in that folder (all private to the user; the folder can be kept in git). Chats saved as single files in the older `conversations` and `archives` layout are converted into folders, with their Claude session logs, when Chat lists them. `OMARCHY_CHAT_CLAUDE_ARGS` adds Claude Code arguments as a JSON array, such as `["--model","opus"]`. To let chats run every tool without asking, as `--dangerously-skip-permissions` does, add `OMARCHY_CHAT_CLAUDE_ARGS='["--permission-mode","bypassPermissions"]'` to `backend.env` and restart the backend; keep the single quotes, or systemd strips the inner ones.
- `CODEXBAR_BIN` defaults to `/usr/bin/codexbar`. Set it to a wrapper that accepts the same arguments and prints the same JSON to change what the CodexBar app reports, for example combined usage across several accounts.
- `SHELL` selects the terminal shell. The installed service uses `/bin/bash` with the user's login configuration and starts in their home directory. Agent-specific environment and the proxy secret are removed from child shells.

The optional TUI programs are `btop`, `systemctl-tui`, `lazydocker`, `dua`, and `lnav` (tested with lnav 0.14.1). Lnav starts `journalctl --no-pager -f -n 1000 -o short-iso` using its command capture. Lnav waits for a frontend `ready` message after screen restoration and sizing, so its startup capability queries reach the client. Child PTYs receive host-side cursor-query replies so startup does not depend on a connected browser; frontend DSR replies are suppressed to avoid duplicate input.

Install the Services dependency with `cargo install systemctl-tui --locked` (tested with 0.7.0) as the backend user. It runs without sudo and shows both system and user units; host permissions govern service actions.

Build with `cargo build --release --manifest-path backend/Cargo.toml`. Run through the enabled `omarchy-remote.service`. Restart that service after changing Rust; running PTYs end on restart. Restart `omarchy-remote-dev.service` after proxy/server changes. Web asset saves require neither restart.

Validation:

```
cargo test --manifest-path backend/Cargo.toml
cargo clippy --manifest-path backend/Cargo.toml --all-targets -- -D warnings
npm run test:backend
npm run test:ui
npm run build && npm test
```

Backend integration tests require the services and local Herdr. They create a dedicated temporary Herdr workspace with `focus:false`, send test commands only there, and remove it afterward. Browser tests type into a separate shell and read existing Herdr panes without sending input to agents.

Sources: [xterm.js API](https://xtermjs.org/docs/api/terminal/classes/terminal/), [portable-pty API](https://docs.rs/portable-pty/latest/portable_pty/), and the installed `herdr api schema --json` contract.

## Browser adapters

`GET /api/browser/snapshot` returns connected adapter instances with windows,
workspaces and tabs. `POST /api/browser/action` accepts `instance_id`, `action`
(create/close/focus/reload/pin/mute/move), and the relevant live `tab_id`,
`window_id`, `url`, `value` or `index`. Workspace writes require the adapter's
`workspace_write` capability. Commands use per-connection IDs, expiry and explicit
acknowledgments. A timeout is ambiguous; refresh before retrying.

The Vivaldi extension uses native messaging through the same Rust binary
(`--browser-bridge`) and `$XDG_RUNTIME_DIR/omarchy-remote-browser.sock` (0600,
peer UID checked). `OMARCHY_BROWSER_SOCKET` supports isolated testing. No proxy
secret is passed to the browser. See `browser-extension/README.md` for installation,
profile configuration, Vivaldi workspace metadata and URL-only phone navigation.
